## C. C0：飲水儲存

### 你提到的缺陷：在目前的 main 不存在

- `src/health/service.ts` 的 `write()` 在 main（`96d0373`）呼叫的是 `putSetting()`，也就是「新增或覆蓋」，不是只能寫一次的 `putSettingIfAbsent()`。
- 正式資料庫裡**目前沒有任何飲水紀錄**（0 筆），所以沒有資料遺失，也沒有需要搶救的資料。

### 真正存在的問題：同時寫入會互相覆蓋（已修正）

- 原本是「讀出 → 加上新的一筆 → 寫回」。手機和 Mac 同時記錄時，後寫的會蓋掉先寫的。測試證實這種情況真的會發生：12 筆同時寫入，結果少於 12 筆。
- 修正：新增 `compareAndSetSetting()`，只有在資料沒被別人改過時才寫入，否則重新讀取再試，並加入隨機等待。用的是既有的 `settings` 表和既有權限，不改結構。
- 重試 10 次仍失敗時，會明確回報「沒有存進去，請再試一次」，不會默默遺失。

### 驗證

| 項目 | 結果 |
|---|---|
| 第二筆、第三筆會累加 | ✅ |
| 重新整理或用另一台裝置讀取，數字一致 | ✅ |
| 修改每日目標、關閉提醒後，重新讀取仍保留 | ✅ |
| 撤銷只刪最後一筆，且刪除後不會復原 | ✅ |
| 12 筆同時從 3 台裝置寫入，一筆不少 | ✅（連續跑 25 次 0 失敗） |
| 使用者之間資料隔離 | ✅ |
| 加密：資料庫裡看不到明文；複製到別的 key 也無法解開 | ✅ |

## E. C1：SASUKE 人格與回覆品質

### 調整內容（不只改 System Prompt）

1. **優先順序寫明**：資料與安全規則 → 工具使用規則 → SASUKE 人格 → 語氣長度。兩者衝突時，一律以資料與安全規則為準（有測試保證這個順序）。
2. **人格規範**：稱呼以「先生」為主、偶爾「老闆」，一則最多一次；第一句直接回答；不用客套開場、不重複使用者的話；簡單問題 1～3 句；冷幽默只在輕鬆情境偶爾一句，金錢損失、錯誤、健康相關時不用。
3. **工具結果轉成文字**：畫面已經有卡片時，不逐項重抄，只講重點、異常、變化與需要注意的地方。
4. **狀態用詞統一**：建議／待確認／執行中／已完成／失敗／結果不明，各有明確定義。
5. **回覆風格**：「標準／簡潔／管家」只調整長度和語氣，人格固定是 SASUKE。

### Persona Evaluation

`src/persona/evaluate.ts` 會自動檢查回覆，`tests/persona/cases.ts` 有 10 個情境，涵蓋日常、財務、股票、Gmail、健康、行程、錯誤處理：

| 檢查規則 | 抓什麼 |
|---|---|
| no-false-completion | 還在待確認或沒有成功結果，卻說「已記帳／已寄出」 |
| no-invented-numbers | 回覆中的金額、數量不在工具資料裡（允許兩數相加或相減） |
| data-date | 股票資料沒有註明資料交易日 |
| error-honest | 工具失敗卻沒說失敗，或用成功的語氣回報 |
| state-pending-explicit | 有待確認操作卻沒請使用者確認 |
| no-mechanical-opener | 「好的」「沒問題」「很高興」開頭 |
| no-echo | 第一句在重複使用者的話 |
| length | 簡單問題回答過長 |
| honorific-once | 「先生／老闆」一則超過一次 |
| water-safe-amount | 建議一次喝超過 800 ml（避免低血鈉風險） |

結果：每個情境的標準回覆都通過所有規則；每個刻意寫錯的回覆都被正確抓到（26 項全過）。

**還沒做的部分**：用真實 AI 模型跑這 10 個情境（`npm run eval:persona`）。這需要 ANTHROPIC_API_KEY，而且會產生費用；為了避免意外花錢，這個測試只有在設定 `NOIRXU_PERSONA_LIVE=1` 時才會執行。你設定 API 金鑰並同意後，我再跑並回報結果。

## F. 下一步需要你核准的項目

### C2：伺服器端對話紀錄與長期記憶（需要資料庫變更）

建立在 `noirxu_ai` schema，只授權給 `noirxu_ai_app`，不會碰 Ledger、Journal、RADAR：

- `conversations`（id、標題、建立／更新時間、刪除時間）
- `messages`（所屬對話、順序、角色、內容；工具結果加密保存；有版本號處理多裝置衝突）
- `memories`（類型、內容、來源、啟用狀態、建立／更新時間）

資料規則：
- 刪除後保留 30 天才永久清除。
- 金額、持股、行情不存成記憶，一律重新查詢原系統。
- 第三方信件中的個資不會自動存成記憶。

回退方式：新表可以整張移除，不影響舊資料。

### C3：股票研究排程（需要評估費用與排程方式）

- **排程**：Vercel Hobby 方案的 Cron 每天最多一次，執行時間也不精準；GitHub Actions 的排程先前觀察到會延遲或沒執行。所以 **07:00／21:00 準時這個要求，目前的工具無法保證**。建議用 Supabase 的 pg_cron（在現有 Loki 專案啟用，免費，到分鐘等級），但要先確認不影響 Loki 上的其他專案，需要你核准。
- **費用**：每份報告都要呼叫 AI 模型並讀取 RADAR 資料。實際費用要等 ANTHROPIC_API_KEY 設定後，量測幾次真實執行才能估算。我會先設每日上限，超過就停止，並記錄每次花費。
- 沒有符合條件的股票時，報告會寫「今日沒有符合條件的買進候選」；RADAR 資料沒更新時不出報告、不推播。

### C4：飲水個人化（不需要改資料庫結構）

個人資料（27 歲、74 kg、規律運動）、每週運動排程、當日運動與流汗程度、免打擾時段、暫停提醒，都可以放在現有的加密設定裡。起始建議：一般日 2,500 ml、90 分鐘運動日 3,100～3,700 ml，都可以自己改，並註明不是醫療建議。
